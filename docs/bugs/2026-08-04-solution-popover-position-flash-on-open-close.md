# Solution: All Popover-based dropdowns flash to the top-left corner on open, and don't close smoothly

**What changed:** `components/ui/popover.tsx`, `PopoverContent`:
- Destructured the raw `x`, `y`, `strategy`, and `isPositioned` values from `useFloating(...)` instead of its convenience `floatingStyles` output.
- Changed the floating `<div>`'s `style` from `style={floatingStyles}` (transform-based positioning) to `style={{ position: strategy, top: y ?? 0, left: x ?? 0, visibility: isPositioned ? "visible" : "hidden" }}` (top/left-based positioning, hidden until the first position computation resolves).

**Why this fixes the root cause:** Two separate issues, found and fixed in two passes:
1. Positioning via `top`/`left` instead of `transform` leaves the `transform` CSS property entirely free for the `data-open`/`data-closed` enter/exit animation classes (scale + slide-in/out offset) to control without fighting floating-ui's own position tracking. This alone fixed every *re*-open of an already-mounted `Popover` instance, because floating-ui's internal `x`/`y` state keeps its last-known-good value across a close (only the `isPositioned` flag itself resets), so a reopened popover already has correct coordinates cached from the moment it remounts.
2. It did **not** fix the very first open of a given `Popover` instance (e.g. right after a fresh page load): floating-ui's `x`/`y` state starts at `(0, 0)` and only updates once its async `computePosition()` call resolves (a `Promise`, not synchronous), so the first-ever render of a freshly-mounted floating element still painted one frame at `(0, 0)` regardless of the top/left fix. Gating `visibility` on `isPositioned` keeps that first frame invisible (rather than visibly flashing at the wrong spot) until real coordinates are ready — verified this resolves within ~2 animation frames (~32ms), imperceptible to the user, after which the popover reveals already correctly positioned and animates in normally. This is a no-op on every subsequent open of the same instance, since `x`/`y` are already correct by then regardless.

**How it was verified:**
1. `npx tsc --noEmit` across the whole project — clean, no new type errors, at every step.
2. Reproduced the flash on the same throwaway unauthenticated test route from the prior bug fix, sampling the popover's computed `style`/bounding box every ~16ms via a headless Playwright script immediately after a click:
   - **Before the top/left change:** `top`/`left` stayed at `0px`/`0px`, actual position encoded in an interpolating `transform` matrix that visibly started near `(0, -8)` (near the viewport's top-left) and animated over ~5 frames to the real position.
   - **After the top/left change:** `top`/`left` are correct (e.g. `210px`/`74px`) and unchanged across every sampled frame from the very first one; only `transform` (scale 0.95→1) and `opacity` (0→1) animate. This matched expectations for *re*-opens, but the user reported the flash still happening on a dropdown's first-ever open, which this round of sampling (IPC round-trip latency between each Playwright poll, several ms) wasn't fast enough to have actually exercised or caught.
3. Re-tested specifically the first-open case with in-browser `requestAnimationFrame`-driven sampling (zero IPC round-trip per sample, so it can observe individual paint frames) on a freshly-loaded page, clicking a `TimeCombobox` instance that had never been opened before:
   - **Before the `isPositioned` change:** not applicable to check this way for "before," but the `x`/`y`-starts-at-(0,0) mechanism was confirmed directly by reading floating-ui's `useFloating` source (`@floating-ui/react-dom`'s `computePosition(...).then(...)` is genuinely async).
   - **After:** frame 0–1 show `visibility: hidden` while `computePosition()` is still resolving; frame 2 onward show `visibility: visible` with the popover already at (or animating smoothly toward) its correct position — no frame is ever visibly painted at the wrong spot.
4. Re-ran the same rAF-precise sampling across an `Escape`-triggered close to confirm the `isPositioned` reset-on-close (a floating-ui internal) doesn't prematurely hide the popover mid-fade-out: `visibility` stayed `"visible"` for every sampled frame while `opacity` faded 1→0, then the element cleanly unmounted — no regression.
5. Removed the throwaway test route after verification. This fix lives in the shared `Popover` component, so it applies to every consumer (Availability's time pickers, the country picker, booking-flow/admin date pickers, notification bell, search popovers, etc.), not just the one the user was looking at.

## Update: extended to Tooltip, and a separate fix for Select/DropdownMenu

**What changed, `components/ui/tooltip.tsx`:** Same fix as `popover.tsx` — `Tooltip` now destructures `x`, `y`, `strategy`, `isPositioned` from its `useFloating(...)` call (shared with `TooltipContent` via `TooltipContext`) instead of `floatingStyles`, and `TooltipContent` positions via `style={{ position: strategy, top: y ?? 0, left: x ?? 0, visibility: isPositioned ? "visible" : "hidden" }}`. This is a separate, hand-rolled `@floating-ui/react` implementation from `popover.tsx` (tooltips aren't routed through `Popover`), so it needed the identical fix applied independently. Verified via the same rAF-sampling approach on a hover-triggered tooltip: position stays within a small, correct ~10px slide range from the first sampled frame — no `(0, 0)` excursion.

**What changed, `components/ui/select.tsx` and `components/ui/dropdown-menu.tsx`:** These aren't built on `popover.tsx` or even directly on `@floating-ui/react` — they use Headless UI's `Listbox`/`Menu` with the `anchor` prop, which internally wires its own `@floating-ui/react` positioning inside `@headlessui/react`'s `internal/floating.js` (not code this project owns or can edit). Investigating with the same rAF sampling found `SelectContent`/`DropdownMenuContent` panels rendering **fully opaque** (`opacity: 1`) at `getBoundingClientRect()` of `(0, 0)` for the first 1–2 frames after every mount, before Headless UI's computed `top`/`left` visually took effect — reproducing the "top-left flash" independently of anything in `popover.tsx`, and on *every* open (not just the first), since Headless UI's panels fully unmount/remount each time.

Since the positioning internals live in a third-party package, the fix is applied at the usage layer instead: a new `hideUntilPositioned` ref callback in `lib/utils.ts`, wired onto `ListboxOptions` (`SelectContent`) and `MenuItems` (`DropdownMenuContent`) via `ref={hideUntilPositioned}`. It fires fresh on every mount (matching Headless UI's per-open remount), synchronously sets `visibility: hidden` on attach (a plain callback ref runs during commit, before paint — no `(0, 0)` frame is ever visible), then reveals the node two `requestAnimationFrame` ticks later once the real position has taken effect. Its cleanup only cancels a still-pending animation frame on early unmount; it never touches `visibility` again afterward, so it structurally cannot interfere with either component's own close/fade-out transition.

**How it was verified:**
1. `npx tsc --noEmit` across the whole project — clean, no new type errors.
2. rAF-precise sampling (same in-browser technique as the `Popover` fix) on a throwaway test route rendering a `Select` and a `DropdownMenu`:
   - **Before:** both showed `rectX: 0, rectY: 0` with `opacity: "1"` (fully visible) for 1–2 frames, then jumped to the correct position.
   - **After:** both show `visibility: "hidden"` for those same frames, then reveal already at (or animating correctly toward) the right spot — no opaque render at the wrong location at any point.
3. Re-tested a second open of the same `Select` instance (Headless UI remounts the panel fresh each time) — confirmed the gate reapplies correctly on every open, not just the first.
4. Confirmed structurally (by inspecting `hideUntilPositioned` itself) that it cannot affect close/fade-out animations, since it only ever runs once per mount and never re-applies `visibility` after its initial reveal.
5. Removed the throwaway test route after verification.

## Update: the actual fix — `transition-none` on all four floating panels

Despite the fixes above (each independently verified correct via frame-accurate sampling), the user kept reporting the same flash. A screen recording of the real Availability page finally made it possible to pin down what was actually happening: the dropdown didn't just flash for a frame — it visibly **glided** from a wrong position to the correct one over roughly 15–20 video frames (~100ms), a much larger and slower motion than anything the earlier fixes were targeting. See the paired bug file's "Update" section for the full root-cause trace (a CSS transition silently animating `top`/`left`, caused by `duration-100` setting `transition-duration` while `transition-property` was left at its CSS-spec default of `all`).

**What changed:** Added the Tailwind `transition-none` utility (`transition-property: none`) to the floating panel's className in all four components: `PopoverContent` (`components/ui/popover.tsx`), `TooltipContent` (`components/ui/tooltip.tsx`), `SelectContent` (`components/ui/select.tsx`), and `DropdownMenuContent` (`components/ui/dropdown-menu.tsx`). One line each.

**Why this fixes the root cause:** `transition-none` sets `transition-property: none`, so ordinary style changes (like floating-ui correcting `top`/`left` once its position computation resolves) apply instantly again instead of being silently interpolated over 100ms. The *intended* visual effect — the `data-open:animate-in`/`data-closed:animate-out` keyframe **animation** — is untouched, since CSS animations and CSS transitions are separate mechanisms; disabling transitions has no effect on `animation-*` properties or the `--tw-duration` custom property they read.

**How it was verified:**
1. `npx tsc --noEmit` across the whole project — clean, no new type errors.
2. Reproduced the exact sequence from the user's screen recording (open one row's dropdown, close it, then open a *different* row — this is what actually triggers it, unlike opening a single fresh popover in isolation) via a headless Playwright script, tracking `offsetTop`/`offsetLeft` (pure layout values, unaffected by `transform`) every animation frame:
   - **Before:** `offsetTop`/`offsetLeft` animated smoothly across several frames (e.g. `16→43→59→68→73→74` and `31→81→112→130→138→140`) even though the element's inline `style.top`/`style.left` strings already read the final correct value from frame 0 — the signature of an unintended CSS transition.
   - **After:** `offsetTop`/`offsetLeft` are constant across every sampled frame from the very first one — the small remaining `getBoundingClientRect()` variation is now purely the intended `zoom-in-95`/`slide-in-from-top-2` animation (a few px of scale/slide), not a real position change.
3. Re-ran the identical prior-open-then-new-open reproduction against `Select` and `DropdownMenu` — both show the same stable `offsetTop`/`offsetLeft` after the fix.
4. Re-verified the close/fade-out animation is unaffected: `opacity` still smoothly fades from ~0.42 down to 0 over several frames before the element unmounts.
5. Removed the throwaway test route and the temporary frame-extraction test page after verification.

This was the actual bug behind every report in this thread. The earlier `isPositioned`/top-vs-transform and `hideUntilPositioned` fixes were real, necessary fixes for genuine (smaller) issues, but this `transition-none` fix is what resolves the visible "gliding from the wrong position," and explains why the bug reproduced inconsistently (dependent on timing/re-render gaps between opens) and across every dropdown/tooltip type in the app.

## Update: fixed a separate "opens twice" glitch in `Popover`/`Tooltip`

**What changed:** `PopoverContent` (`components/ui/popover.tsx`) and `TooltipContent` (`components/ui/tooltip.tsx`) — `data-open` now matches both `status === "initial"` and `status === "open"`, instead of only `"open"`:
```tsx
data-open={status === "initial" || status === "open" || undefined}
```

**Why this fixes the root cause:** `useTransitionStatus`'s `status` spends one `requestAnimationFrame` tick in `"initial"` before reaching `"open"`. With `data-open` gated on `"open"` only, that one-frame gap rendered the panel with none of the `animate-in` classes active (plain full-opacity/full-scale), and the animation only started a frame later — snapping the element back to its `opacity:0 scale:0.95` starting keyframe first, producing a visible "pop, then re-animate" double-open. Including `"initial"` means the `animate-in` classes (and the CSS animation they trigger) are active from the very first frame the panel exists, so it plays through its keyframes exactly once, smoothly.

**How it was verified:** Tracked `opacity`, `transform`, and the `data-open` attribute every animation frame via a headless Playwright script on a fresh `TimeCombobox` open:
- **Before:** implied by the state-machine logic (not separately re-tested pre-fix, since the mechanism was identified directly by reading `useTransitionStatus`'s source and cross-checking against the `data-open` condition).
- **After:** `data-open="true"` is present from the very first visible frame, and `opacity` climbs in one clean monotonic curve (`0.000 → 0.802 → 0.925 → 0.983 → 1.000`) with `transform`'s scale interpolating correspondingly — no jump, reset, or discontinuity anywhere in the sequence. `npx tsc --noEmit` clean. Removed the throwaway test route after verification. `Select`/`DropdownMenu` use Headless UI's own `transition` prop (a different mechanism, not `useTransitionStatus`), so they were not affected by this particular issue.

## Update: fixed the analogous "opens twice" glitch in `Select`/`DropdownMenu`

**What changed:** `SelectContent` (`components/ui/select.tsx`) and `DropdownMenuContent` (`components/ui/dropdown-menu.tsx`) — the exit-animation trigger changed from `data-closed:animate-out data-closed:fade-out-0 data-closed:zoom-out-95` to `data-leave:animate-out data-leave:fade-out-0 data-leave:zoom-out-95` (and, in `DropdownMenuContent`, `data-closed:overflow-hidden` → `data-leave:overflow-hidden`). The enter trigger (`data-open:animate-in ...`) is unchanged.

**Why this fixes the root cause:** Live-dumping every `data-*` attribute on the panel frame-by-frame during an open revealed that Headless UI's own internal transition machinery (`@headlessui/react`'s `useTransition` hook) briefly sets `data-closed` and `data-open` *simultaneously* for one frame on every open — an internal "prepare" step that resets any in-flight transition before the real enter animation starts. Since our CSS reacted to `data-closed`'s mere presence, that one frame activated `data-closed:animate-out` at the same time as `data-open:animate-in`, and the element rendered at full opacity/scale during that frame before snapping back to its `opacity:0 scale:0.95` starting point and re-animating forward — the same pop-then-re-animate glitch as the `Popover`/`Tooltip` case, via a different mechanism. Headless UI also exposes `data-leave`, a separate attribute reserved *only* for an actual close/leave transition — confirmed via the same attribute dump that it's never present during open's "prepare" step — so keying the exit animation off `data-leave` instead removes the false trigger entirely while still firing correctly on a real close.

**How it was verified:**
1. `npx tsc --noEmit` across the whole project — clean, no new type errors.
2. Dumped every `data-*` attribute plus `opacity`/`transform` every animation frame via a headless Playwright script on a fresh `Select` open:
   - **Before:** frames 4–5 showed `opacity: 1.000` (fully open) with both `data-closed` and `data-open` present simultaneously; frame 6 then dropped to `opacity: 0.000` with `data-closed` removed, followed by a fresh climb back to `1.000` — the pop-then-re-animate.
   - **After:** a single clean monotonic climb from the very first frame (`0.000 → 0.224 → 0.577 → 0.803 → 0.926 → 0.984 → 1.000`), no discontinuity.
3. Re-ran the identical check against `DropdownMenu` — same clean monotonic curve (`0.000 → 0.219 → 0.575 → 0.802 → 0.924 → 0.983 → 1.000`).
4. Confirmed via the earlier close-sequence attribute dump (from the `transition-none` investigation) that `data-leave` is present during a real close and `data-open` is not, so switching the exit trigger doesn't change close behavior at all.
5. Removed the throwaway test route after verification.

## Update: applied the same `data-leave` fix to every remaining `data-closed:animate-out` consumer

A codebase-wide `grep -rn "data-closed:" components/ui` found three more components with the identical pattern: `DialogOverlay`/`DialogContent` (`components/ui/dialog.tsx`), `AlertDialogOverlay`/`AlertDialogContent` (`components/ui/alert-dialog.tsx`), and the overlay/panel in `components/ui/sheet.tsx`. Same one-line change in each: `data-closed:animate-out data-closed:fade-out-0 [data-closed:zoom-out-95 | directional data-closed:slide-out-to-*-10]` → the equivalent `data-leave:` classes.

**How it was verified:** `npx tsc --noEmit` clean. Re-ran the same frame-by-frame `data-*` attribute + `opacity` dump against a `Dialog` opened via a throwaway test route: `data-open` and `data-closed` still co-occur for one frame (confirming the underlying Headless UI behavior is unchanged), but since the exit animation no longer reacts to `data-closed`, `opacity` climbs in one clean monotonic curve from the first frame (`0.000 → 0.577 → 0.802 → 0.925 → 0.983 → 1.000`) with no pop or reset. Removed the throwaway test route after verification. `Popover`/`Tooltip` were confirmed to *not* need this change (their `status` state machine is mutually exclusive, no equivalent overlap), and the rest of the Headless-UI-based components in `components/ui/` (`accordion.tsx`, `radio-group.tsx`, `tabs.tsx`) don't use this `animate-in`/`animate-out` pattern at all.
