# Bug: All Popover-based dropdowns flash to the top-left corner on open, and don't close smoothly

**Where:** Every consumer of `components/ui/popover.tsx` (`Popover`/`PopoverContent`) — the Availability page's `TimeCombobox` dropdowns, `CountryCombobox`, the booking-flow date picker, `bookings-date-filter.tsx`, `notification-bell.tsx`, `global-search.tsx`, settings search, the admin email client's date range picker, etc. Reported by the user against the Availability page's time dropdown right after the previous "dropdown doesn't open" fix: on open, the dropdown visibly appears near the page's top-left corner for a moment before jumping to its correct position below the trigger; on close it wasn't smooth either.

**How it was found:** Recreated the same throwaway unauthenticated test route used for the previous bug (`TimeCombobox` rows, mirroring the Availability page), and used a headless Playwright script to sample the popover content element's computed `style`/bounding box every ~16ms immediately after clicking a trigger. The inline `style` always showed `top: 0px; left: 0px` with the real position encoded entirely via `transform: matrix3d(...)` (`translate(74px, 210px)` etc. baked into the matrix) — confirming `useFloating`'s default transform-based positioning strategy (`floatingStyles`). Across the first ~5 frames, the captured `transform` matrix interpolated from something close to `translate(0, -8px) scale(0.95)` up to the real `translate(74px, 210px) scale(1)`, exactly matching the "starts near top-left, ends at the real spot" symptom.

**Root cause:** `PopoverContent` (`components/ui/popover.tsx`) applied `style={floatingStyles}` from `useFloating`, which positions the element via an inline `transform: translate(x, y)` rather than `top`/`left`. Separately, the same element's className includes Tailwind/tw-animate-css enter/exit animation utilities (`data-open:animate-in data-open:zoom-in-95 data-[side=bottom]:slide-in-from-top-2`, `data-closed:animate-out data-closed:zoom-out-95`, etc.) that *also* animate the `transform` property via CSS keyframes (scale + a small slide offset). A running CSS animation takes over the animated property's value for its full duration, so the keyframe's own transform (interpolating from a small offset near `(0,0)` up to its resting `translate3d(0,0,0)`) completely masked floating-ui's positioning transform while the ~100ms open/close animation played — the popover rendered near the viewport's top-left corner until the animation finished, at which point the inline `style.transform` (the real position) became visible again, producing a visible jump. The same conflict made the close animation incorrect (whatever it looked like was governed by the animation's own transform values, not by floating-ui's tracked position).

## Update: the flash persisted on first open, and turned out to affect every dropdown type, not just Popover

After the fix above, the user reported the flash still happening specifically the *first* time any dropdown was opened (subsequent opens were fine), and — per a follow-up — on **every** dropdown in the app, not just the `Popover`-based ones.

**Second root cause (first-open only, `Popover`-based dropdowns):** `useFloating`'s `x`/`y` position state starts at `{x: 0, y: 0}` and only updates once its internal `computePosition()` call — genuinely asynchronous (`@floating-ui/react-dom`'s `floating-ui.react-dom.esm.js`, `computePosition(...).then(...)`) — resolves. The very first time a given `Popover` instance opens, there is no previously-computed position yet, so the first rendered frame used the stale `(0, 0)` default regardless of the top/left fix above. On a *re*-open of the same still-mounted instance, `x`/`y` already hold their last-known-good value (only an internal `isPositioned` flag resets on close, not the coordinates), which is why reopens never showed the flash. Confirmed via frame-accurate `requestAnimationFrame` sampling from inside the browser (Playwright's own polling had too much IPC round-trip latency to have ever actually observed this).

**Third root cause (every dropdown, including `Select`/`DropdownMenu`/`Tooltip`):** `components/ui/select.tsx` and `components/ui/dropdown-menu.tsx` don't use `components/ui/popover.tsx` at all — they're built on Headless UI's own `Listbox`/`Menu` with its `anchor` prop, which internally uses `@headlessui/react`'s own `@floating-ui/react` wiring (`internal/floating.js`, not something this codebase can patch). That internal implementation already avoids the transform-conflict bug (it passes `transform: false` to its own `useFloating` call), but still renders the panel **fully opaque** at `(0, 0)` for the first 1–2 frames after every mount, before its computed `top`/`left` visually take effect — worse than the `Popover` case since it isn't masked by a fade-in (opacity was already `1`). Since Headless UI's panels fully unmount on every close (not just first-ever open), this reproduced on *every* open, matching the "anywhere, every time" report. `components/ui/tooltip.tsx` has the same first/second root cause as `Popover` (it's a separate hand-rolled `@floating-ui/react` implementation, not routed through `popover.tsx` either) — same `floatingStyles`/no-`isPositioned` pattern, just for tooltips instead of popovers.

## Update: the actual everywhere-reproducible bug — `duration-100` silently transitioning `top`/`left`

Despite the fixes above (independently verified correct via frame-accurate sampling), the user kept reporting the same flash. A screen recording of the real Availability page finally made it possible to pin down what was actually happening: the dropdown didn't just flash for a frame — it visibly **glided** from a wrong position to the correct one over roughly 15–20 video frames (~100ms), a much larger and slower motion than anything the earlier fixes were targeting.

Reproducing the exact sequence from the video (open a *different* row's dropdown, close it, then open the row that glitched) confirmed it live: `getBoundingClientRect()` — and critically, `offsetTop`/`offsetLeft` (pure layout values, never affected by `transform`) — animated smoothly from one position to another across ~5 frames, even though the element's inline `style.top`/`style.left` strings read the correct final value (`"140px"`/`"74px"`) from the very first sampled frame. That combination — the *target* value being correct immediately, but the *rendered/laid-out* value animating toward it — is the signature of a CSS **transition** on `top`/`left`, not a positioning computation bug at all.

The cause: `className` on each of these floating panels includes Tailwind's `duration-100` utility, needed to feed the `--tw-duration` CSS custom property that `tw-animate-css`'s `animate-in`/`animate-out` keyframe *animation* duration falls back to (`animation-duration: var(--tw-animation-duration, var(--tw-duration, .15s))`). But `duration-100` is fundamentally a Tailwind **transition** utility — it also sets the literal CSS `transition-duration: 100ms` property. None of these components' classNames ever set an explicit `transition-property` (only `transition-colors` appears elsewhere, unrelated to these elements). Per the CSS spec, `transition-property`'s initial/default value is `all` — so with `transition-duration: 100ms` set and `transition-property` left at its default, **any** change to an animatable property (including the `top`/`left` floating-ui writes as inline styles once its async position computation resolves) gets smoothly interpolated by the browser over 100ms, instead of applying instantly.

This explains everything observed across this whole investigation:
- Why it looked "fixed" in earlier isolated tests: a single freshly-mounted popover's `top`/`left` update (from its `(0, 0)` default to the real computed value) often happened fast enough — before the browser's first paint — that there was no "old" rendered value for the browser to transition *from*, so no visible animation occurred.
- Why it reliably reproduced after a *previous* popover had just been opened and closed, and in the user's real usage (a page with many mounted comboboxes, more re-renders, more timing variance): enough of a gap opened up between an initial paint and the corrected position for the CSS transition to actually become visible and glide.
- Why the user saw it on *every* dropdown type in the app: `Popover`, `Tooltip`, `Select`, and `DropdownMenu` all independently apply the same `duration-100` + `data-open:animate-in`/`data-closed:animate-out` pattern to their floating panel's className.

## Update: a distinct "opens twice" glitch, separate from the position bug

After the `transition-none` fix, the user confirmed positioning was fixed but reported a new (or previously-masked) symptom: the open animation itself looked like it played twice in quick succession — a fast pop, then a re-animate.

**Root cause:** `PopoverContent`/`TooltipContent` derive `data-open` from floating-ui's `useTransitionStatus`, whose `status` state machine goes `"unmounted" → "initial" → "open"` — deliberately spending one `requestAnimationFrame` tick in `"initial"` before reaching `"open"` (this two-step is intended for consumers who drive inline styles directly off `status`, per floating-ui's own docs pattern). But `data-open` was only set for `status === "open"`, not `"initial"`. During that one-frame `"initial"` gap, neither `data-open` nor `data-closed` matches any selector, so the panel rendered with none of the `animate-in` utility classes active — i.e., at its plain, undecorated full-opacity/full-scale appearance. One frame later, `status` flips to `"open"`, `data-open` gets added, and the `animate-in` CSS *animation* starts playing — snapping the element back to its `opacity: 0, scale: 0.95` starting keyframe before animating forward to full again. The net visible effect: pop in at full size → snap back small/transparent → animate back in — read by the user as "opens twice."

## Update: the same "opens twice" glitch in `Select`/`DropdownMenu`, via a different mechanism

The `Popover`/`Tooltip` fix didn't touch `Select`/`DropdownMenu` — the user confirmed the Availability page's time pickers were now smooth, but pointed out the "Working Hours (default)" schedule-switcher `<Select>` (and other `Select`/`DropdownMenu` menus) still had the same pop-then-re-animate glitch on open.

**Root cause:** `SelectContent`/`DropdownMenuContent` key their enter/exit animation classes off `data-open:animate-in ...` and `data-closed:animate-out ...`. Tracing Headless UI's own internal transition state machine (`@headlessui/react`'s `hooks/use-transition.js`) with a live attribute dump across animation frames showed that on *every* open, Headless UI briefly sets **both** `data-open` and `data-closed` simultaneously for one frame — an internal "prepare" step that intentionally resets any in-flight transition state before the real enter animation starts. Since our CSS reacts to `data-closed` presence alone (regardless of `data-open` also being present), `data-closed:animate-out` and `data-open:animate-in` were both active during that one frame, and — mirroring the `Popover`/`Tooltip` bug exactly — the element rendered at full opacity/scale during that "prepare" frame, then snapped back to `opacity:0 scale:0.95` and re-animated forward once `data-closed` was removed a frame later.

Headless UI also exposes `data-enter`/`data-leave`, its own purpose-built transition-phase attributes — verified via the same attribute dump that `data-leave` is *only* ever present during an actual close (never during open's "prepare" step, unlike `data-closed`), making it the correct exit-animation trigger.

## Update: the same bug in every remaining `data-closed:animate-out` consumer

Next reported against the Availability page's "Advanced settings → Timezone" control, which turned out to be a `Dialog` (`components/ui/dialog.tsx`), not a dropdown at all — confirming the underlying `data-closed`+`data-open` co-occurrence is a property of Headless UI's shared `useTransition` hook, affecting every component built on it, not just menu-style floating panels. A codebase-wide search (`grep -rn "data-closed:" components/ui`) found the identical `duration-100 data-open:animate-in ... data-closed:animate-out ...` pattern in three more places: `DialogOverlay`/`DialogContent` (`dialog.tsx`), `AlertDialogOverlay`/`AlertDialogContent` (`alert-dialog.tsx`), and the overlay/panel in `sheet.tsx`. `Popover`/`Tooltip` still legitimately use `data-closed` (their `status` state machine from `useTransitionStatus` is mutually exclusive — `status` is never simultaneously `"open"` and `"close"` — so there's no equivalent overlap there); `accordion.tsx` and the rest of the Headless-UI-based components (`radio-group.tsx`, `tabs.tsx`) don't use this `animate-in`/`animate-out` pattern at all.
